# ADR-0005: Детерминированный Detection Engine

- Статус: принято
- Дата: 2026-07-22

## Контекст

Control plane уже принимает нормализованные события идемпотентно. Этап 5 должен создавать
инциденты без повторного разбора сырого journald `MESSAGE`, без исполняемых выражений в
правилах и без нарушения атомарности ingestion. Повторная доставка одного `event_id` и
конкурентные запросы не должны порождать повторные инциденты или evidence.

## Решения

1. Detection работает только с сохранённым контрактом `NormalizedEventV1` и пятью
   поддерживаемыми `event_type`. Агент и разбор journald на этом этапе не меняются.
2. YAML загружается через `yaml.safe_load` и закрыт строгими Pydantic-моделями с
   `extra="forbid"`. Разрешены ровно `single`, `threshold`, `distinct_count`, `sequence` и
   `first_seen`. `eval`, `exec` и произвольные выражения отсутствуют.
3. Все временные окна используют `occurred_at` и включают обе границы:
   `trigger - window <= occurred_at <= trigger`. Sequence дополнительно требует, чтобы
   предыдущий шаг произошёл строго раньше следующего шага.
4. Любая выборка истории ограничена `server_id`. Отсутствующее или `null` обязательное
   поле correlation, grouping, distinct value или first-seen scope отменяет совпадение.
5. В каталоге `detection-rules` находятся восемь версионированных journald-правил.
   Nginx source/parser и два зависящих правила остаются отложенными; десять end-to-end
   правил не заявляются.
6. `validate-rules` проверяет весь каталог без подключения к БД. `sync-rules` сначала
   валидирует все файлы, вычисляет SHA-256 канонического JSON, затем одной транзакцией
   добавляет отсутствующие версии и переключает активную версию каждого `rule_key`.
   Один каталог не может содержать два файла одного `rule_key`, даже с разными версиями.
   Обычный startup правил не синхронизирует.
7. Опубликованная строка `detection_rule_versions` рассматривается как immutable.
   Новая конфигурация требует нового положительного `version`; совпадение `(rule_key,
   version)` с другим checksum отклоняется.
8. Ingestion использует PostgreSQL `INSERT ... ON CONFLICT DO NOTHING ... RETURNING Event`.
   Detection получает только фактически вставленные строки. Existing-события не проходят
   повторную оценку.
9. Event, `last_used_at`, detection, incident и evidence находятся в одной транзакции
   ingestion. Ошибка движка или persistence приводит к rollback всего batch и безопасному
   HTTP 503 без payload в логах.
10. Correlation содержит только перечисленные в правиле поля и канонизируется в JSON.
    SHA-256 correlation hash вместе с `server_id` и `rule_version_id` определяет активный
    инцидент.
11. Частичный unique index PostgreSQL допускает не более одного инцидента со статусом
    `new`/`investigating` для server/rule-version/correlation. Transaction-level advisory
    lock от этих трёх значений берётся до чтения history и выполнения правила. Поэтому
    ожидавшая lock транзакция читает уже committed события предыдущей транзакции. Lock
    освобождается при commit или rollback.
12. Повторное совпадение добавляет только новые строки `incident_events`, сохраняет
    минимальный `first_seen_at`, максимальный `last_seen_at` и пересчитывает `event_count`
    по уникальным evidence. Snapshot, версия, заголовок и рекомендации уже созданного
    инцидента не переписываются. Событие, обработанное новой версией правила, создаёт или
    обновляет отдельный инцидент этой версии.
13. На этапе 5 движок создаёт только статус `new`. Status API, audit history, RBAC,
    Telegram, dashboard и outbox worker отложены.

## Последствия и ограничения

- Правила становятся активными только после явного локального `sync-rules`.
- История запрашивается из PostgreSQL отдельно для каждого нового trigger/rule. Это
  простое и проверяемое решение MVP; пакетная оптимизация потребует измерений.
- Advisory locks и partial indexes делают конкурентную дедупликацию PostgreSQL-специфичной.
- Rule snapshot сохраняет объяснимость старого инцидента. Миграция существующего активного
  инцидента и добавление в него evidence новой версии намеренно не выполняются.
- Incidents read/status API пока отсутствует; проверка выполняется SQL и тестами.
