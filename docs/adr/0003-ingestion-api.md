# ADR-0003: Аутентифицированный Ingestion API

- Статус: предложено к подтверждению по итогам этапа 3
- Дата: 2026-07-21

## Контекст

Control plane должен принимать нормализованные события только от зарегистрированных
агентов, безопасно обрабатывать повторную и параллельную доставку и не раскрывать ключи
или payload в логах. Redis и отдельная очередь в MVP отсутствуют.

## Решения

1. Единственная точка приёма этапа 3 — `POST /api/v1/events`. Входным контрактом является
   `EventBatchV1`, а идентификатор сервера определяется только по проверенному API-ключу.
2. Заголовок аутентификации имеет строгий формат
   `Authorization: Bearer wgak_<public_id>.<secret>`. По `public_id` выполняется один поиск,
   после чего digest проверяется существующей constant-time функцией.
3. Неизвестный ключ, неверный secret, отзыв и истечение срока возвращают одинаковый
   безопасный ответ. Неактивный сервер возвращает отдельный `403` только после успешной
   проверки ключа.
4. ASGI middleware проверяет `Content-Type` и читает body с жёсткой верхней границей до
   передачи данных JSON parser. Тело запроса и Authorization не журналируются.
5. Каждый запрос получает безопасный request ID. Он доступен обработчику, добавляется в
   заголовок и тело ответа и явно присутствует в журнале запроса.
6. `sent_at` должен находиться в конфигурируемом интервале относительно UTC-времени
   control plane. `collected_at` каждого события не может быть позднее верхней границы
   этого интервала. Нижняя граница для времени событий отсутствует, чтобы агент мог
   доставлять накопленную локальную очередь после восстановления связи.
7. Контракт `NormalizedEventV1` отклоняет U+0000 в `actor`, `summary`, а также во всех
   строковых ключах и значениях `attributes` на любой глубине. Символ не заменяется и не
   удаляется: это сохраняет однозначность данных и предотвращает несовместимую с
   PostgreSQL JSONB запись.
8. Весь пакет и обновление `last_used_at` находятся в одной SQLAlchemy-транзакции.
   Неожиданная ошибка PostgreSQL откатывает обе операции.
9. События вставляются одним PostgreSQL statement с
   `ON CONFLICT DO NOTHING` по `(server_id, agent_event_id)` и `RETURNING`. Это позволяет
   отдельно вернуть числа новых и уже существовавших событий.
10. Rate limit на этапе MVP является потокобезопасным process-local окном, ключом которого
   служит аутентифицированный `public_id`. Счётчик обновляется сразу после успешной
   аутентификации и учитывает запрос, даже если тот позднее отклонён проверкой clock skew.
   Лимит и длительность окна задаются конфигурацией.
11. Тестовый сервер и ключ создаются только локальным CLI. Plaintext-токен выводится один
    раз и не сохраняется в PostgreSQL. HTTP admin API не создаётся.
12. Обязательные интеграционные сценарии выполняются отдельным Docker test target на
    настоящем PostgreSQL. SQLite не используется.

## Последствия и ограничения

- Идемпотентность обеспечивается самой уникальностью PostgreSQL и работает между
  конкурентными транзакциями.
- Process-local rate limiter подходит одному процессу MVP, но не даёт глобального лимита
  при горизонтальном масштабировании или нескольких worker-процессах.
- Запросы, отклонённые middleware или JSON/контрактной валидацией до вызова endpoint, не
  доходят до аутентифицированного rate limiter. Для них в MVP требуется ограничение на
  perimeter/reverse proxy.
- Ограничитель body буферизует не более настроенного лимита до JSON parsing; для текущего
  максимума пакета это проще и безопаснее потокового частичного разбора.
- Ingestion API только сохраняет события. Агент, detection engine, outbox worker,
  Telegram и dashboard остаются за границей этапа 3.
