# ADR-0004: Надёжный Linux Agent для journald

- Статус: принято
- Дата: 2026-07-21

## Контекст

Агент должен переживать потерю сети и перезапуск без продвижения journald cursor раньше
локального сохранения события. Он работает с чувствительными системными журналами и не
должен превращаться в канал передачи окружения, команд или секретов.

## Решения

1. Единственная подтверждённая платформа MVP — Ubuntu Server 24.04 LTS с systemd.
2. Источники реализуют общий `JournalSource`. Единственный реальный адаптер MVP запускает
   фиксированный `/usr/bin/journalctl` списком аргументов, без shell и без настраиваемой
   команды. Файловые auth.log/secure и Nginx parser не входят в этап.
3. Continuous mode читает journal в две фазы. Сначала отдельный конечный вызов без
   `--follow` выгружает все доступные записи после сохранённого cursor. После атомарного
   сохранения каждой записи агент заново читает последний committed cursor и запускает
   `--follow --lines=all --after-cursor=...`. Поэтому записи, появившиеся между процессами
   `journalctl`, входят в начало follow-выдачи. На самом первом запуске backlog читается с
   `--lines=all`; ограниченный tail разрешён только явной команде `run-once`.
4. Некорректный или исчезнувший cursor не вызывает тихий fallback. Агент сначала
   увеличивает постоянный безопасный diagnostic `journal_gap`, затем явно удаляет старую
   точку продолжения и начинает rebase. Diagnostic не содержит cursor, `MESSAGE` или
   stderr `journalctl`. Ротация уже удалённых записей остаётся необратимой потерей и
   требует внимания оператора через `spool-status`.
5. SQLite работает в WAL и `synchronous=FULL`. Одна `BEGIN IMMEDIATE` транзакция сначала
   вставляет событие, затем обновляет cursor и только после этого выполняет `COMMIT`.
   Намеренно пропущенная неизвестная запись продвигает cursor отдельной короткой
   транзакцией. Если `event_id` уже надёжно есть в spool, cursor повторно прочитанной записи
   обновляется и фиксируется в той же транзакции, не создавая второй строки.
6. `event_id` детерминированно строится как UUIDv5 от journald cursor. Primary key spool
   предотвращает повторное сохранение и бесконечный replay дубликата после перезапуска.
7. Очередь ограничена числом записей. При заполнении newest запись не сохраняется, cursor
   не двигается, сбор приостанавливается. Автоматического удаления oldest нет.
8. `MESSAGE` читается только локально для явного распознавания пяти классов: неудачный и
   успешный SSH-вход, ошибка аутентификации sudo, создание пользователя, изменение
   привилегированной группы `sudo`/`adm`/`wheel`. В событие попадают фиксированный
   `event_type`, фиксированный шаблон `summary`, проверенные actor/source IP и небольшой
   allowlist атрибутов. Неизвестный или содержащий U+0000 `MESSAGE` пропускается целиком;
   исходный текст, произвольная команда, environment и секреты не копируются ни в summary,
   ни в attributes.
9. На POSIX каталог spool принадлежит пользователю процесса и имеет `0700`. Существующая
   БД должна быть обычным не-symlink файлом того же владельца. БД создаётся с `0600` до
   открытия SQLite; `-wal` и `-shm` проверяются и приводятся к `0600`. systemd дополнительно
   задаёт `UMask=0077` и `StateDirectoryMode=0700`.
10. Production transport принимает только HTTPS, читает credential из отдельного private
    token file, задаёт connect/read timeout и отправляет пакеты 1–100 событий с уникальным
    request ID.
11. Строки удаляются только после валидного HTTP 200, где `accepted + existing` совпадает с
    размером пакета. `422` изолируется делением batch; одиночное событие quarantine и
    остаётся в spool. Аналогично одиночный `413` получает статус oversized.
12. `429` использует `Retry-After`; network/5xx/protocol errors используют exponential
    equal-jitter backoff. `401/403` получают отдельную длинную паузу.
13. SIGTERM устанавливает общий stop event, завершает journald subprocess и collector, но
    не удаляет неподтверждённые строки. Неожиданное падение collector останавливает процесс
    с ненулевым кодом и безопасным сообщением, чтобы `Restart=on-failure` запустил агент
    повторно без вывода исходного payload.
14. systemd запускает отдельного пользователя без capabilities. Чтение journal даётся
    через стандартную read-only группу `systemd-journal`; token file принадлежит агенту и
    имеет права не шире `0600`.
15. Операторские команды `spool-status`, `spool-list --status`, `spool-requeue` и
    `spool-delete` работают локально без чтения token file. List показывает только UUID,
    status, attempts и безопасный error code. Delete требует повторить точный event UUID в
    `--confirm`; полный payload команды не печатают.
16. Nginx source/parser и два зависящих от него detection-правила перенесены в следующий
    релиз. До их отдельной реализации и теста нельзя заявлять десять end-to-end правил MVP.

## Последствия и ограничения

- Членство в `systemd-journal` даёт чтение доступного system journal, поэтому границей
  минимизации данных служат явные парсеры поддерживаемых событий.
- Quarantined/oversized строки сохраняются и занимают bounded spool до явного requeue или
  подтверждённого delete.
- При устаревшем cursor и уже ротированном journal возможен неизбежный разрыв. Постоянный
  `journal_gap` делает этот факт видимым, но не может восстановить удалённые записи.
- Реальный journald/systemd test требует отдельного Ubuntu Server 24.04 стенда. В текущей
  среде выполняются только синтетические fixtures и тест fixed-command adapter.
- Архитектура допускает будущий файловый адаптер, но одновременное чтение одного события
  из journald и файла не реализуется.
