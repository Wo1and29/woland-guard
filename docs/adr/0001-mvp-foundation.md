# ADR-0001: Базовая архитектура Woland Guard

- Статус: принято
- Дата: 2026-07-21

## Контекст

Woland Guard создаётся как защитная система мониторинга собственных Linux-серверов.
Первый этап должен дать минимальный воспроизводимый каркас без реализации сбора событий,
моделей данных, ingestion API и detection engine.

## Решения

1. Проект создаётся только в каталоге `D:\kwork\woland-guard`.
2. Основная целевая система агента — Ubuntu Server 24.04 LTS.
3. Агент и control plane используют только Python 3.12 на этапе MVP.
4. Control plane строится как модульный монолит на FastAPI. Dashboard, API и будущая
   доменная логика разделяются модулями, но не отдельными сетевыми сервисами.
5. Основной будущий источник агента — journald. Источники будут реализовывать общий
   интерфейс адаптера; одновременно активируется только один адаптер для одного потока,
   чтобы journald и файловые журналы не создавали дубли.
6. PostgreSQL является единственным обязательным инфраструктурным хранилищем MVP.
7. Redis и RQ не используются.
8. Надёжные фоновые операции будут реализованы через PostgreSQL transactional outbox:
   состояния `pending`, `processing`, `delivered`, `failed`; конкурентный захват через
   `SELECT FOR UPDATE SKIP LOCKED`; ограниченные повторы, exponential backoff,
   последняя ошибка и идемпотентный ключ. Реализация outbox не входит в этап 1.
9. `/health/live` проверяет только состояние процесса. `/health/ready` выполняет
   минимальный `SELECT 1` к PostgreSQL и не раскрывает текст внутренней ошибки.
10. Контейнер control plane работает от непривилегированного пользователя, с удалёнными
    Linux capabilities и read-only root filesystem.
11. Документация MVP пишется на русском языке.
12. Лицензия пока не добавляется, поэтому проект не называется open-source.

## Явно исключено из MVP

- автоматическая блокировка;
- Docker socket;
- PDF-отчёты;
- React;
- Redis и специализированные очереди;
- SaaS, биллинг и multi-tenancy;
- реальные токены, пароли, персональные журналы и пользовательские IP-адреса.

## Последствия

- Уменьшается число обязательных компонентов и эксплуатационная сложность.
- PostgreSQL worker потребуется аккуратно тестировать на конкурентный захват и возврат
  зависших записей из `processing`.
- Файловый адаптер auth.log/secure можно добавить без изменения основной логики агента,
  но он не входит в первый этап.
- Версии Python-зависимостей фиксируются в `uv.lock`; Docker-сборка обязана использовать
  `uv sync --locked` и завершаться ошибкой при рассинхронизации lock-файла.
