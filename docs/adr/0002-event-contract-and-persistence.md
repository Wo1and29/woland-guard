# ADR-0002: Контракт событий и схема хранения

- Статус: принято
- Дата: 2026-07-21

## Контекст

До появления ingestion API и Linux-агента необходимо зафиксировать независимый контракт
нормализованного события и воспроизводимую схему PostgreSQL. Схема должна поддерживать
идемпотентный приём событий и будущую надёжную доставку уведомлений без Redis.

## Решения

1. Общие Pydantic-контракты находятся в отдельном workspace-пакете
   `woland-guard-contracts`. Первая версия контракта явно содержит `schema_version = 1`.
2. В контракте MVP разрешён только источник `journald`. Сервер не передаёт собственный
   `server_id`: в будущем ingestion API определит сервер по ключу агента.
3. Временные метки обязаны содержать часовой пояс. Пакет ограничен 100 событиями и не
   может содержать повторяющиеся `event_id`.
4. Таблица `events` хранит исходный нормализованный payload в PostgreSQL `JSONB`, а поля
   для идемпотентности и основных запросов вынесены в отдельные типизированные столбцы.
5. Повтор события определяется уникальной парой `(server_id, agent_event_id)`.
6. Ключ агента состоит из публичного идентификатора и случайного секрета. В PostgreSQL
   сохраняется только SHA-256 digest случайного высокоэнтропийного секрета. Этот подход
   не предназначен для паролей пользователей.
7. Таблица transactional outbox содержит состояния `pending`, `processing`, `delivered`,
   `failed`, счётчики попыток, время следующей попытки, данные блокировки, последнюю ошибку
   и уникальный идемпотентный ключ.
8. Схема изменяется только версионированными миграциями Alembic. Начальная миграция имеет
   как `upgrade`, так и `downgrade`.

## Последствия и границы этапа

- Контракт не зависит от будущих HTTP routes и может использоваться агентом отдельно.
- PostgreSQL-специфичный `JSONB` намеренно исключает SQLite как эквивалентную среду
  интеграционного тестирования.
- Наличие таблицы outbox ещё не обеспечивает доставку: конкурентный worker,
  `SELECT FOR UPDATE SKIP LOCKED`, backoff и восстановление зависших записей будут
  реализованы позднее.
- Управление серверами и ключами через HTTP, ingestion API, агент и detection engine
  не входят в этап 2.
