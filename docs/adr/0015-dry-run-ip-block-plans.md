# ADR-0015: dry-run блокировка IP через Telegram

- Статус: принято, реализовано в 9C (9C-1 домен/БД, 9C-2 Telegram)
- Дата: 2026-08-02
- Дополнено: ADR-0016 закрыл оставленный здесь открытым вопрос об исполнении — автоматическое
  исполнение не реализуется, dry-run остаётся единственным режимом навсегда.

## Контекст

Исходное техническое задание требует функцию блокировки IP: dry-run по умолчанию, allowlist
доверенных адресов, запрет блокировать localhost/собственный адрес сервера/адрес администратора,
audit всех действий, подтверждение опасных операций. До 9C этой функциональности не было ни в
каком виде (подтверждено grep по `iptables|nftables|firewall|allowlist` — 0 совпадений в `apps/`),
что было честно зафиксировано в `docs/threat-model.md`.

9C реализует только предложение и подтверждение плана. **Ничто в control plane не исполняет
`command_argv`** — это принципиальная граница подэтапа, а не временное упущение. Вопрос о реальном
исполнении был оставлен здесь открытым и решён отдельно в ADR-0016: исполнение **не
реализуется**, применение подтверждённой команды остаётся действием человека.

## Решения

### Источник адреса — не ввод оператора, а correlation инцидента

1. Адрес для блокировки берётся из `Incident.correlation["source_ip"]`, а не запрашивается у
   оператора. Оператор физически не может назвать произвольный адрес через кнопку — это резко
   сужает поверхность атаки по сравнению с текстовым вводом. Поле `source_ip` есть у 5 из 8
   действующих правил (`ssh_bruteforce_by_ip`, `ssh_password_spray_by_ip`,
   `ssh_login_from_new_ip`, `ssh_root_login_success`, `ssh_success_after_failures`); у инцидента
   без этого поля кнопка отвечает «нет адреса источника», а не создаёт план.
2. `IncidentCreatedNotificationV1` (application/outbox.py) документирован как payload, который
   **не может включать correlation-данные** — он широковещательный, уходит всем получателям
   канала без привязки к конкретному оператору. Поэтому кнопка «Подготовить блокировку IP»
   **не может появляться условно**: адаптер, формирующий исходящее уведомление, не знает и не
   должен знать, есть ли у инцидента адрес источника. Кнопка присутствует на клавиатуре всегда;
   при нажатии на инцидент без адреса оператор получает явный, безопасный ответ. Расширять payload
   полем `source_ip` было отклонено как решение — это отправило бы адрес атакующего в broadcast,
   нарушив собственный инвариант payload'а.

### Never-block — явный список, а не свойства `ipaddress`

3. `application/ip_block_policy.py` держит захардкоженный кортеж сетей с комментарием на каждую
   запись (loopback, link-local, RFC1918/ULA, multicast, reserved, documentation-диапазоны,
   Teredo/6to4), а не полагается только на `ipaddress.IPv4Address.is_private`/`is_reserved` и
   подобные свойства. Эти свойства менялись между версиями Python (например, для 100.64.0.0/10),
   а security-критичный allowlist должен читаться в ревью построчно и тестироваться поимённо, а не
   зависеть от поведения стандартной библиотеки, которое не документировано как стабильный
   контракт для целей блокировки. Свойства `is_*` всё равно проверяются — как вторая, независимая
   страховка, а не замена явному списку.
4. Неканоничные формы адреса **отклоняются, а не нормализуются**: IPv4-mapped IPv6
   (`::ffff:203.0.113.5`), адрес со scope_id (`fe80::1%eth0`), любая строка, для которой
   `str(ip_address(value)) != value`. Нормализация дала бы второй путь к одному и тому же адресу и
   обошла бы рассуждение о never-block, построенное на каноническом представлении.
5. **Честное ограничение, задокументированное явно, а не спрятанное**: `demo/scenarios.py`
   генерирует `source_ip` из документационных диапазонов (`192.0.2.0/24`, `203.0.113.0/24`) —
   именно тех, что never-block запрещает по построению. Демо-сценарий блокировки должен либо
   показывать этот отказ как есть, либо использовать отдельный, вне-документационный синтетический
   адрес — то и другое честнее, чем тихо обходить собственную защиту в демонстрационных целях.

### Allowlist и RBAC

6. Allowlist («адрес администратора» и любые доверенные диапазоны из ТЗ) управляется только через
   локальный CLI (`add-ip-allowlist-entry`/`revoke-ip-allowlist-entry`/`list-ip-allowlist-entries`),
   тем же способом, что operator API keys и Telegram-привязки. Control plane нигде не хранит IP
   операторов (проверено grep по `ip_address|client_ip|remote_addr|INET` — только
   `demo/scenarios.py`), поэтому «адрес администратора» невозможно вывести автоматически; это
   зафиксировано как явное эксплуатационное требование в `docs/deployment.md`, а не подразумевается
   работающим само по себе.
7. Две новые `Permission`, без третьей «на будущее»: `PROPOSE_IP_BLOCK` (analyst и admin) и
   `APPROVE_IP_BLOCK` (только admin, через `ROLE_PERMISSIONS[ADMIN] = frozenset(Permission)`).
   **Отклонить план требует только `PROPOSE_IP_BLOCK`, не `APPROVE_IP_BLOCK`**: отказ от опасного
   действия — безопасное направление, тот же аналитик, что мог предложить план, может его отозвать
   без второго администратора. Подтвердить может только admin. Заводить третью Permission для этой
   асимметрии избыточно — два права уже её выражают.
8. Одобрение по умолчанию требует **другого** оператора, чем предложивший
   (`WG_IP_BLOCK_REQUIRE_SECOND_OPERATOR=true`), с возможностью отключить для установок с одним
   администратором. Это единственная реализация «подтверждения опасных операций» из ТЗ, которая не
   зависит от доверия к самому себе.

### Идемпотентность — доменная, без второго механизма

9. Ни `propose_ip_block`, ни `approve_ip_block`/`reject_ip_block` не используют
   `operator_idempotency_records` (в отличие от `transition_incident`). Идемпотентность построена
   на самой схеме: частичный уникальный индекс `(incident_id, ip_address) WHERE status='proposed'`
   делает повторное «Подготовить» на живой план чистым чтением без записи и без нового audit
   (`REUSED`); решение (`approve`/`reject`) идемпотентно через проверку `status != 'proposed'`,
   так что повторная доставка того же `callback_query` (at-least-once поверх Telegram) естественно
   получает «план уже обработан», а не повторное действие. Заводить второй механизм поверх этого
   было бы дублированием уже достаточной защиты.
10. Гонка двух одновременных первых предложений для одного `(incident_id, source_ip)` устраняется
    `pg_advisory_xact_lock`, той же техникой, что `_acquire_correlation_lock` в детекторе
    (`application/detection/engine.py`) уже использует для похожей проблемы «прочитать, решить,
    вставить». Повторное использование существующего в кодовой базе паттерна, а не изобретение
    нового.
11. Истёкший, но ещё не решённый план **не получает отдельного статуса** `expired` — статус
    остаётся `proposed`, а истечение проверяется по `expires_at <= now` в момент чтения (тот же
    приём, что `telegram_pending_actions` из 9B). Из этого следует: повторное «Подготовить» на
    истёкший план обновляет ту же строку на месте (новый `command_argv`, новый `proposed_by`, новый
    `expires_at`) вместо вставки второй строки — партиционный уникальный индекс иначе не позволил
    бы вставку, пока старая строка числится `proposed`. Технически это одна и та же строка,
    семантически — новый цикл предложения, поэтому пишется новый audit.

### Повторная проверка политики при подтверждении — обязательный шаг

12. `approve_ip_block` заново вызывает `classify_block_target` перед тем, как перевести план в
    `approved` — allowlist мог измениться между предложением и подтверждением, и это изменение
    обязано победить. Это не оптимизация и не защита от гонки, а требование корректности: план,
    предложенный до попадания адреса в allowlist, не должен становиться подтверждаемым только
    потому, что он уже лежит в БД.
13. Если повторная проверка проваливается, план **автоматически переводится в `rejected`**
    (с audit `ip_block_plan.rejected`, не `.approved`), а не остаётся в `proposed`. База никогда не
    хранит план, который выглядит одобряемым, но политикой уже запрещён.

### Главный текстовый инвариант — явное «не выполнено»

14. Ответ на «Подтвердить» **обязан** прямо утверждать, что блокировка не выполнена
    (`formatting.IP_BLOCK_APPROVED_TEXT`, `"НЕ выполнена"` заглавными). Это единственная защита от
    самого опасного возможного недопонимания в этом подэтапе: оператор решает, что адрес уже
    заблокирован, хотя control plane физически не может это сделать. Инвариант закрыт unit-тестом
    (`test_approved_outcome_explicitly_states_nothing_was_executed`).

### Команда — nftables, фиксированный argv, показанный, но не вызываемый

15. `build_nft_block_command` строит `["nft", "add", "element", "inet", <table>, <set>, "{",
    <ip>, "}"]` — элемент множества, не правило. Идемпотентно по построению (повторное добавление
    того же элемента не создаёт дубликат), в отличие от `iptables -I`. Set выбирается по семейству
    адреса (`blocked_v4`/`blocked_v6`); имена таблицы и обоих set — конфигурация
    (`WG_IP_BLOCK_NFT_*`), провалидированная тем же regex `^[a-z][a-z0-9_]{0,31}$`, что и сама
    команда проверяет перед сборкой — двойная защита на случай рассинхронизации.
16. `" ".join(argv)` для отображения, не `shlex.join` — инвариант «ни один токен не содержит
    пробела» (табличные/set-имена ограничены regex, адрес каноничен, остальное — константы)
    делает кавычки `shlex.join` избыточными и менее читаемыми оператором. Инвариант закрыт тестом
    (`test_build_nft_block_command_selects_the_set_by_address_family`).
17. **Честное ограничение**: control plane не создаёт таблицу `inet <table>` и оба set сам — это
    было бы изменением firewall без ведома администратора. Их создание — ручной шаг при установке,
    описанный в `docs/deployment.md`. Если таблицы или set нет, показанная команда не сработает
    при ручном применении — ответственность за подготовку сервера лежит на администраторе
    (см. также ADR-0016: применение команды в принципе остаётся ручной операцией).

### Изменение модели угроз

18. До 9C ни один correlation-производный элемент не покидал control plane через Telegram.
    С 9C `source_ip` может появиться **в личном чате аутентифицированного оператора, прошедшего
    RBAC-проверку, по его явному нажатию кнопки** — и только там; broadcast-уведомления
    (`format_incident_created_message`) по-прежнему его не содержат. `docs/threat-model.md`
    обновлён этим пунктом явно, а не молча.

### Побочная находка — decode-поведение psycopg3 для `inet`/`cidr`

19. psycopg3 по умолчанию декодирует колонки `inet`/`cidr` в объекты `ipaddress.IPv4Address`/
    `IPv6Address`/`IPv4Network`/`IPv6Network`, а не в `str`, даже когда модель SQLAlchemy объявляет
    `Mapped[str]` — расхождение между объявленным и рантайм-типом. Найдено чтением исходников
    `psycopg/types/net.py` и `sqlalchemy/dialects/postgresql/psycopg.py` до написания моделей, а не
    отладкой постфактум. Исправлено `native_inet_types=False` в `database.py`, чтобы весь проект
    продолжал единообразно работать со строковыми идентификаторами, как и все остальные колонки.

## Границы 9C

- Исполнения нет ни в каком виде — ни автоматического, ни по кнопке «Подтвердить». Кнопка
  подтверждения меняет только статус строки в БД.
- Редактирование/удаление уже отправленного follow-up-сообщения с планом после решения не
  реализовано — повторное нажатие кнопки на уже решённый план получает «план уже обработан» через
  `answerCallbackQuery`, но сами кнопки в чате остаются видимыми (та же граница, что ADR-0014
  зафиксировал для кнопок статуса инцидента в 9B).
- Причина отклонения не запрашивается — только подтверждение или отклонение одним нажатием.
- Создание таблицы/set в nftables на сервере — ручной шаг администратора, не автоматизировано.
- Ничего не меняется в REST API, Dashboard, HTMX/JavaScript или LICENSE.
