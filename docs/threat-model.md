# Модель угроз

Каждый пункт ниже — то, что действительно проверено в коде и ADR, а не заявленное намерение.
Если смягчение реализовано частично, это указано явно, со ссылкой на источник.

## Кража API-ключа агента (`wgak_...`)

PostgreSQL хранит только SHA-256 digest секрета (ADR-0002, ADR-0003); plaintext токен выводится
CLI один раз и не сохраняется. Blast radius кражи ограничен одним сервером: украденным ключом
можно только слать события от имени *этого* `server_id`. Ключ можно отозвать/деактивировать
через `is_active`/`revoked_at`, событие фиксируется в audit log.

**Остаточный риск:** нет автоматической ротации ключей (README, «Ограничения MVP»); нет
детектирования аномального использования уже валидного украденного ключа (нет anomaly
detection по объёму/паттерну событий на уровне самого агента-источника).

## Подделка событий (event forgery)

Агент нормализует `MESSAGE` локально по фиксированным regex-шаблонам до отправки, но ingestion
API доверяет содержимому пакета от аутентифицированного агента — сервер не может независимо
подтвердить, что событие действительно произошло на хосте. Скомпрометированный ключ агента
позволяет создавать произвольные (в рамках схемы `NormalizedEventV1`) события от имени сервера:
ложные инциденты или попытку «утопить» реальный сигнал в шуме.

**Остаточный риск:** это прямое следствие модели «доверенный агент = доверенный источник
событий»; независимой атрибуции события хосту (например, mTLS с client-конкретным сертификатом
поверх Bearer-ключа) не реализовано.

## Повторная отправка запросов (replay)

At-least-once delivery с идемпотентным приёмом: уникальность `(server_id, agent_event_id)` и
`INSERT ... ON CONFLICT DO NOTHING` исключают дублирование событий/инцидентов при повторе
(ADR-0002, ADR-0003). Смена статуса инцидента защищена `Idempotency-Key` с сохранённым
canonical-hash и business-результатом; повтор с другим телом даёт `409` (ADR-0006, §9).

**Остаточный риск:** идемпотентность защищает от дублирования данных, но не от повторного
раскрытия перехваченного валидного пакета атакующим с сетевым доступом — это категория
«компрометация транспорта/ключа», требующая HTTPS в production (агент требует HTTPS URL,
ADR-0004 §10).

## DoS через поток событий

Process-local rate limiter по аутентифицированному `public_id` (ADR-0003 §10), жёсткая верхняя
граница размера тела до JSON-парсинга, пакет ограничен 1–100 событиями, connect/read timeout на
агенте.

**Остаточный риск (задокументировано явно, не скрыто):** limiter не координируется между
несколькими процессами/инстансами control plane; запросы, отклонённые middleware или
JSON/контрактной валидацией до аутентификации, не учитываются лимитом. **Perimeter rate
limiting на reverse proxy остаётся обязательным production-требованием**, которое сам проект не
реализует (ADR-0003, ADR-0007).

## Компрометация Telegram-бота

Bot token никогда не хранится в PostgreSQL, `.env`, CLI-аргументах, audit log или repr; читается
только из отдельного private staging file (ADR-0006 §22). Worker/telegram-admin работают под
UID/GID `10001:10001`, `cap_drop: ALL`, read-only root filesystem, private tmpfs. Production
origin — compile-time константа `https://api.telegram.org`; клиент использует `verify=True`,
`follow_redirects=False`, `trust_env=False` (ADR-0006 §23) — конфигурацией нельзя подменить
endpoint или обойти TLS-проверку. Логгер `httpx2`/`httpcore2` подавлен до создания запроса,
поскольку token находится в URL (ADR-0006 §25, с regression-тестом на canary-значения в логах).
Уведомление содержит только allowlisted envelope (id, rule, severity, заголовок, время) — не raw
event payload, не IP, не credentials (ADR-0006 §27).

С этапа 9A появился **входящий** канал: отдельный процесс читает `getUpdates` тем же
fixed-origin клиентом. Его граница доверия — default deny: отвечает только связанному через
локальный CLI оператору и только в приватном чате; групповые сообщения и сообщения от ботов
отклоняются до открытия сессии PostgreSQL. С 9B любое приватное сообщение с непустым текстом
(не только команда) открывает сессию для аутентификации — это нужно, чтобы обнаружить ожидание
причины терминального статуса, и осознанно расширяет прежнюю границу (ADR-0014, раздел про
поверхность похода в БД); несвязанный аккаунт получает тот же безопасный ответ с его Telegram
ID вне зависимости от содержимого сообщения. Права проверяются той же RBAC-матрицей, что у REST
и Dashboard. Ответы собираются из фиксированных строк и явных колонок БД и никогда не отражают
ввод пользователя. Разбор обновлений ограничен по длине и диапазону, а ошибка разбора не
отражает тело ответа провайдера.

С 9B входящий канал может **менять статус инцидента** через callback-кнопки. `callback_data`
трактуется как недоверенный ввод, а не как значение, которое обязательно положил на кнопку этот
процесс: разбор закрытый, версионированный, отклоняет любое отклонение от канонической формы
целиком (ADR-0014). Мутация переиспользует тот же `transition_incident` и ту же RBAC-проверку
`TRANSITION_INCIDENTS`, что REST и Dashboard — отдельного, более слабого пути для Telegram нет.
Идемпотентность — по `callback_query.id`, которую Telegram гарантирует уникальной, поэтому
повторная доставка одного нажатия не создаёт двойной переход. `expected_version` кнопки статуса
фиксирован на момент отправки уведомления; устаревшая кнопка отклоняется существующей
optimistic-lock проверкой, а не каким-либо клиентским кодом. Причина терминального статуса
запрашивается отдельным сообщением, а не подставляется шаблоном, поэтому audit сохраняет смысл.

**Остаточный риск:** доверие к `telegram_user_id` ограничено доверием к самой платформе: проект
проверяет, что обновление получено от Telegram по TLS с фиксированным origin, но не может
независимо подтвердить личность отправителя за пределами Telegram. Если bot token
скомпрометирован (вне периметра проекта), атакующий может как читать уведомления, так и
выполнять операторские мутации от имени любого связанного оператора — здесь нет второго фактора
сверх самого Telegram-аккаунта; связывание аккаунта с оператором выполняется только локальным
CLI, поэтому произвольный посторонний Telegram-пользователь всё равно не сможет действовать без
явного связывания. Rate limiter входящих сообщений process-local и не координируется между
процессами. Комментарии к инциденту через Telegram недоступны — это следующий подэтап, если
будет реализован.

**С 9C входящий канал может предлагать, подтверждать и отклонять dry-run-план блокировки IP** —
подробности ниже, в разделе «Несанкционированное выполнение блокировки IP». Это меняет модель
угроз: до 9C ни один correlation-производный элемент (в частности, IP-адрес источника события) не
покидал control plane через Telegram — исходящее уведомление содержит только allowlisted envelope
(см. выше). С 9C `source_ip` инцидента может появиться **в личном чате аутентифицированного
оператора, прошедшего RBAC-проверку `PROPOSE_IP_BLOCK`, по его явному нажатию кнопки** — и только
там; broadcast-уведомление о создании инцидента по-прежнему его не содержит и не может содержать
(ADR-0015).

## Несанкционированное выполнение блокировки IP

**Проект не исполняет команды блокировки ни в каком виде, и это окончательное решение, а не
незавершённая работа** (ADR-0016). 9C (ADR-0015) реализует только domain-модель плана и его
подтверждение через Telegram — `IpBlockPlan` со статусами proposed/approved/rejected, never-block
список и allowlist, four-eyes подтверждение (`WG_IP_BLOCK_REQUIRE_SECOND_OPERATOR`, по умолчанию
включено). Ни один процесс проекта не вызывает `command_argv`, который лишь показывается оператору
как текст; применение команды остаётся действием человека.

Риск несанкционированного исполнения отсутствует структурно — исполняющего кода не существует, а
не он существует и заблокирован предохранителем. Единственный процесс, способный исполнить команду
на защищаемом хосте, — агент, и он по построению парсит недоверенный ввод (строки `sshd` в journald
порождает удалённый участник). Выдача такому процессу `CAP_NET_ADMIN` потребовала бы снять три
независимые защиты в его systemd-юните (`CapabilityBoundingSet=`, `AmbientCapabilities=`,
отсутствие `AF_NETLINK` в `RestrictAddressFamilies=`) и нарушила бы ADR-0004 §14. Полный разбор
рассмотренных альтернатив и условия, при которых решение стоит пересматривать, — в ADR-0016.

**Отдельно отмечено в ADR-0016:** автоматическая блокировка по адресу из логов сама является
инструментом атаки — вызвав события от имени нужного адреса, атакующий добивается его блокировки.
Для SSH это трудно (нужен полноценный TCP-handshake), но для запланированного источника `nginx`
`source_ip` в общем случае берётся из заголовков, контролируемых клиентом. Это дополнительная
причина не исполнять блокировку автоматически, независимая от вопроса о привилегиях агента.

Средства защиты уже в 9C: адрес берётся только из `Incident.correlation["source_ip"]`, не из
ввода оператора; never-block — явный захардкоженный список сетей (loopback, приватные, link-local,
multicast, reserved, документационные диапазоны), проверяемый до allowlist и не обходимый
конфигурацией; allowlist управляется только локальным CLI; подтверждение плана заново
перепроверяет политику (allowlist мог измениться) и автоматически отклоняет план, если адрес
больше не подлежит блокировке; функция полностью выключена по умолчанию
(`WG_IP_BLOCK_ENABLED=false`).

**Остаточный риск:** «адрес администратора», который ТЗ требует защитить от блокировки,
control plane не может определить автоматически — он нигде не хранит IP операторов. Это
эксплуатационное требование: администратор обязан добавить свой адрес в allowlist через CLI сам
(`docs/deployment.md`). Если этого не сделать, адрес администратора в принципе блокируем той же
логикой, что и любой другой публичный адрес.

## Утечка логов

Последовательно проведено через весь код: Authorization/body не логируются в ingestion API
(ADR-0003 §5); audit details строятся только из закрытого allowlist полей, не из HTTP body или
event payload (ADR-0006 §10, §66); агент не копирует `MESSAGE`, environment, command line или
произвольные journald-поля в исходящий payload (`apps/agent/README.md`, «Защита данных»); токен
и payload агента исключены из `repr`, контролируемых логов и текста исключений; Telegram-логгер
подавлен на уровне namespace, а не через фильтрацию сообщений постфактум.

**Остаточный риск:** сам системный `journald` на хосте содержит значительно больше данных, чем
агент реально считывает и парсит — граница минимизации данных проходит по явным парсерам агента,
а не по правам доступа к журналу (агент состоит в группе `systemd-journal`, которая технически
даёт read-доступ ко всему журналу; ADR-0004, «Последствия и ограничения»). Как оператор
настраивает агрегацию логов самого control plane (`docker compose logs`, внешний log shipper) —
вне периметра проекта.

**Отдельно про Nginx access log (ADR-0020).** Это первый источник, где строка описывает
произвольный HTTP-запрос, а не системное событие, поэтому граница минимизации задана жёстче:

- query-строка отбрасывается целиком **до** формирования события — не фильтруется по списку
  известных имён параметров, потому что имя параметра с секретом заранее неизвестно
  (`?token=`, `?t=`, `?auth=` одинаково правдоподобны);
- `$http_referer`, `$http_user_agent` и `$remote_user` не извлекаются вообще: они не нужны ни
  одному правилу, и «прочитать на будущее» противоречило бы ADR-0004 §8;
- путь обрезается до 256 символов и передаётся только если состоит из печатных ASCII-символов.

**Остаточный риск:** путь — это пространство URL, которым управляет оператор. Если приложение
размещает одноразовый секрет в сегменте пути (`/reset-password/<токен>`), а не в query-строке,
он попадёт в атрибуты события. Проект сознательно не угадывает секреты внутри пути эвристикой по
энтропии: ложное срабатывание молча испортило бы полезные пути, а пропуск всё равно оставил бы
риск. Оператору, чьё приложение так устроено, следует это учитывать при включении источника.

## SQL injection

Весь доступ к PostgreSQL идёт через SQLAlchemy 2 ORM/Core с параметризованными запросами; сырые
`text()`-запросы (например, в `pipeline.py` demo-инструментов) используют bind-параметры, а не
конкатенацию строк. Ruff `S`-правила (bandit-эквивалент) включены в CI и ловят наиболее очевидные
паттерны небезопасного построения запросов.

**Остаточный риск:** нет отдельного SAST-инструмента, специализированного на поиске SQL
injection (semgrep/bandit сверх Ruff `S`), — это не критично при дисциплинированном
использовании ORM, но не формально доказано статическим анализом.

## XSS

Dashboard рендерится через Jinja2 с включённым по умолчанию autoescape. Отдельно и независимо от
экранирования — строгий Content-Security-Policy без `inline script`/`inline style` и без внешних
ресурсов (ADR-0007 §11): даже при обходе экранирования исполнение inline-скрипта заблокировано
браузером.

## CSRF

Двойная защита: точная проверка `Origin` для unsafe-запросов и session-bound CSRF-токен
(независимый от session token digest), `SameSite=Strict` + `__Host-`-префикс cookies, которые
недоступны cross-origin по конструкции браузера (ADR-0007 §4–5). Изменение статуса инцидента и
добавление комментариев дополнительно требуют `Idempotency-Key`, что делает CSRF-эксплуатацию
через простой auto-submit form практически невозможной даже при обходе Origin-проверки.

## SSRF

Поверхность минимальна структурно: единственный исходящий HTTP-вызов control plane — к Telegram
Bot API с compile-time захардкоженным origin и без follow_redirects (см. выше). Агент отправляет
данные только на предварительно сконфигурированный control-plane URL — сам не проксирует и не
запрашивает произвольные внешние адреса. В 8B demo/verification tooling sender принимает только
явный HTTP/HTTPS loopback origin (README, «Синтетические demo-сценарии»). Нигде в production
runtime оператор или пользователь не может указать произвольный внешний URL, который сервер
затем содержательно запросит.

## Неправильная настройка Docker

Application-контейнеры (`control-plane`, `outbox-worker`, `telegram-admin`) работают под
непривилегированным UID/GID `10001:10001`, с `cap_drop: ALL`, `no-new-privileges:true`,
`read_only: true` root filesystem и tmpfs для `/tmp` (`compose.yaml`). Docker socket нигде не
монтируется — это явное исключение из MVP (ADR-0001). Официальный образ PostgreSQL сохраняет
штатный entrypoint и **не получает** такой же non-root/read-only hardening — это задокументировано
явно, а не скрыто (ADR-0012).

**Остаточный риск:** production reverse proxy и TLS termination оператор должен настроить сам
(README, «пример reverse proxy», «инструкция HTTPS-развёртывания»); нет автоматического
сканирования итогового образа на OS-уровневые CVE в CI — только Python-зависимости через
`pip-audit` (`.github/workflows/ci.yml`).

## Повышение привилегий агента

Агент запускает единственный фиксированный `/usr/bin/journalctl` списком аргументов без shell и
без пользовательской команды — command injection через конфигурацию агента структурно исключён
(ADR-0004 §2). systemd-юнит задаёт `UMask=0077`, `StateDirectoryMode=0700`; SQLite spool
принадлежит пользователю агента с правами `0700`/`0600`; агент работает от системного
пользователя без shell и без capabilities, состоит только в стандартной группе
`systemd-journal`.

**Остаточный риск:** членство в `systemd-journal` даёт read-доступ ко всему системному журналу
хоста, что шире, чем реально считываемые пять классов событий — минимизация данных обеспечена
явными парсерами агента, а не ограничением прав чтения (см. «Утечка логов» выше и ADR-0004).

## Итог

Woland Guard помогает обнаруживать подозрительные события и ускоряет реакцию на инциденты, но
**не заменяет полноценный аудит безопасности и не гарантирует предотвращение всех атак**.
